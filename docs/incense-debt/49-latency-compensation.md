# 49 · 延迟补偿与移动回弹修复

本篇记录 2026-10-13 对双人合作联机“延迟卡顿、移动闪回、步骤闪回、来回行进抽搐”的定位和修复。修复针对客户端的状态呈现，不改变服务器对移动、碰撞、伤害、掉落、房间切换和成长的权威裁定。

## 结论

可以使用延迟补偿，但要把补偿放在正确的层级：本地玩家使用客户端预测和服务器确认后的平滑纠正，远端玩家和场景实体使用带抖动自适应的时间缓冲、插值和短时有界外推。服务器继续以 60 Hz 运行，20 Hz 状态快照和 30 Hz 输入仍通过 ENet/DTLS 的 UDP 战斗链路传输。

这针对客户端显示逻辑制造的回弹和抖动，不能把真实的公网 RTT 变成零。超过缓冲能力的持续丢包、路由拥塞或设备渲染掉帧仍会增加可见延迟。最新 0.6.1 服务端已经同步到公网主机，Windows 修复客户端也已用同一公网服务完成原生流程验证；线上服务端切换与客户端验收见[同步记录](reports/latency-compensation-2026-10-13/online-sync.json)。

## 问题定位

| 症状 | 原因 | 影响 |
| --- | --- | --- |
| 自己移动后突然退回 | 预测位置与权威位置只要达到旧的 140 px 阈值就直接硬切到服务器位置 | 冲刺、推开、短时丢包都会产生明显闪回 |
| 远端角色来回抽搐 | 收到较晚的快照时，渲染时钟仍使用 `lerpf` 向旧服务器时间回退 | 角色在两个快照之间反复往返 |
| 网络抖动时步骤后退 | 自适应 `delay` 增大后，目标渲染时间变小 | 即使快照序号正确，画面也会倒退 |
| 丢一个状态包后再跳跃 | 远端玩家和敌人只有插值，没有短时运动外推；子弹已有外推 | 先停住，下一包到达时一次性跳到新位置 |
| 误以为 UDP 不能丢包 | UDP 只提供传输路径，不提供游戏状态语义 | 丢包、重复和乱序必须由 ENet/状态序号/快照恢复处理 |

Godot 的[官方联机文档](https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html)也明确说明，UDP 数据包可能丢失或乱序；选用 UDP 后仍然需要正确的状态同步和表现策略。

## 已实施的修复

### 本地玩家：预测、重演与平滑纠正

`game/scripts/network/motion_prediction.gd` 仍然重演尚未被服务器确认的输入，因此本地移动不会等待 RTT。收到权威状态后：

* 误差不超过 1.5 px 时直接收敛，避免小数值噪声造成微抖；
* 误差在 1.5—320 px 时保留当前画面位置，以指数衰减速度 11 平滑回到权威位置；
* 320—420 px 的误差把表现偏移限制在 320 px 内后收敛，以避免长时间偏离实际位置；
* 只有达到 420 px 以上，才认为是换房、传送或严重状态断层并硬切；
* 纠正只作用于位置表现，生命、命中、技能、掉落、金币和成长仍直接采用服务器状态。

这样处理后，延迟造成的正常预测误差不会被误判成传送。场景真正切换时，控制器会清理预测和插值历史，避免把上一房间的运动带到下一房间。

### 远端对象：单调时钟和自适应插值

`game/scripts/network/remote_interpolation.gd` 采用 50—220 ms 的有界显示缓冲。缓冲目标由实际 ENet RTT 与快照到达抖动共同决定，变化通过平滑滤波完成。渲染时间具有单调性：

* 晚到的旧服务器时间不能把 `clock` 往回拉；
* 缓冲延迟改变时，`render_time` 不能往回跳；
* 每个实体最多保留 16 个样本，仍按实体序号拒绝旧状态；
* 丢快照时，子弹和远端敌人/玩家最多外推 100 ms，超过后停在安全位置等待绝对状态修复；
* 外推结果仍经过客户端内墙约束，不参与服务器命中判定。

控制器把战斗链路实际测得的 ENet RTT 传入插值器。WSS 只负责引导、身份和恢复，不再用控制平面的 RTT 覆盖战斗延迟。

### 菜单状态变化：暂停去重与一次重试

包体原生回归还复现了一个独立问题：刚恢复战斗后立即打开地图，暂停命令可能仍带着客户端上一份 epoch。服务器会以 `stale_context` 拒绝该命令，因此地图返回时无法进入双方暂停/恢复闭环。控制器现在合并尚未确认的暂停请求，并只在收到此类拒绝时使用新房间状态重试一次。服务器对旧命令的校验保持生效，客户端不会无限重试。

### 权威边界和“服务器回溯”取舍

本轮没有对移动做服务器回溯。移动回溯会让服务器接受已经不符合当前碰撞环境的旧位置，增加穿墙、重复移动和作弊面。服务器仍只接受带有 link、room、match、epoch、scene、lease、sequence 的最新输入，并在自己的 60 Hz tick 中裁定位置。

如果以后需要改善高延迟射击命中，可以单独为命中验证保存极短的服务器历史，并按攻击时间、最大回溯窗口和碰撞层做严格限制；它不应复用玩家移动的视觉纠正逻辑。

## 验证证据

本轮测试没有使用 Docker、WSL 或其他虚拟化环境，也没有连接 Android 真机。通过的检查包括：

* `tests/remote_interpolation.gd`：旧快照不能回退时钟，RTT 增大缓冲但不回退，插值、外推上限和暂停冻结通过；
* `tests/online_combat.gd`：180 px WAN 误差平滑收敛，520 px 场景级断层仍硬切，预测、武器、技能、存档和墙内碰撞通过，`checks=273 failures=0`；
* `tests/state_stream.gd`：状态序号、实体绝对修复、乱序辅助片段、场景切换和弹丸定义通过；
* `tests/cooperative_transport.gd`：三真实 socket 客户端、合作房间、暂停/恢复、成长选择、断线冻结和重连通过，`checks=35 passed=true`；
* `tests/network_faults.gd`：输入租约、旧 epoch/scene/link、状态黑洞、ACK 黑洞、身份接管和唯一结算通过；
* 公网 `wss://xhz-server.sidcloud.cn/play` + UDP `18779` 双 Windows headless 合作烟测：30.589 秒、60.001 Hz、ping P95 51 ms、状态年龄 P95 33 ms、可游玩帧比例 1.0、战斗阻塞超过 100 ms 为 0、客户端错误为空、边缘拒绝为 0。
* 最终 Windows EXE 的真实公网原生流程：29 项通过、0 失败、33 张捕获；覆盖移动、射击、地图返回、断线重连、右手触控、成长选择、双方物理走门与离线存档隔离。[包体验证记录](reports/latency-compensation-2026-10-13/native-client.json)绑定 EXE SHA-256 `f9bf68867d16a48e9d8ad1cabd494dbc3c8863e5c4eacc5912d6b2b5966d9326`。

服务端同步后的健康端点显示 `transport=2`、`battle_encrypted=true`、`combat_stalls_over_100ms=0`，且线上运行二进制 SHA-256 已与本地最新构建一致。服务端同步不改变权威规则，改动集中在客户端表现层。

## 发布边界

源码修复已经完成并通过上述回归。本地 Windows 与 Android 包将绑定版本 0.6.1；本轮线上同步覆盖同版本服务端，Android 真机仍按既定范围未验证。

原生流程捕获证明功能闭环，不等价于完整的弱网手感与渲染帧时间验收。后续发布验收应补充持续往返运动下的纠正次数、最大可见跳变和画面帧时间；这些指标可以进一步区分网络问题、客户端渲染掉帧和设备性能瓶颈。
