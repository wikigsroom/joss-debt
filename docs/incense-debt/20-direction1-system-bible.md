# 方向 01 系统圣经：香火债

本文件是《香火债 / Incense Debt》方向 01 的总装配说明。它把产品承诺、设计数据、固定 Tick 运行时、素材与验收证据串成一条链，供后续新增角色、房间、武器、遗物、UI 和音频时作为唯一的系统入口。详细数值仍以 [`data/catalog.json`](data/catalog.json) 与 [`data/rules.json`](data/rules.json) 为准；本文件解释它们如何共同形成可玩的平面房间肉鸽。

## 1. 产品承诺与爽感

玩家扮演从未还之愿中诞生的纸偶，在三层失控庙宇里完成“看见危险—挂上余烬—连成债链—一次焚债—回收香灰”的循环。每间房都必须让玩家在移动、瞄准、收灰和选供物之间做出即时决定；每次构筑选择都要改变下一间房的可行解，而不是只增加一条被动文字。核心爽感来自四件事：连续命中让标记增长，债链把多个目标变成一个结算单位，焚债在清屏瞬间释放爆发，余烬回收又把资源转成下一次技能。

战斗的可读性优先于数值堆叠。敌方危险有预告、颜色和方向；主攻、次级派生、焚债、灼烧、招架、护甲和击退拥有不同的画面层、音效族与事件来源。所有派生事件受 `proc_depth_cap` 与 `chain_event_cap` 约束，保证“越爽越清楚”，不会因递归效果失去控制。

## 2. 真实权威与边界

`game/data/catalog.json` 和 `docs/incense-debt/data/catalog.json` 必须保持字节一致，保存稳定 ASCII ID、中文名称、路线、触发、模式和内容关系。`game/data/rules.json` 保存固定 Tick、碰撞、掉落、成长、存档、平台预算和事件枚举。World 只从 JSON 建立内容索引，渲染层不能自行发明伤害、掉落或路线条件。

`game/scripts/combat/world.gd` 是运行时结算入口；`effects.gd` 只处理遗物和行愿的规则钩子；`room_graph.gd` 生成物理可走的房间图；`game_renderer.gd`、`modern_ui.gd` 和 `audio_director.gd` 只消费事件并表现它们。设计层的 `specified`、`planned` 或 `design_baseline` 不等于成品验收；软件闭环以[方向 01 运行系统审计](reports/runtime/direction1-system-audit.json)和各专项报告为证据，真人平衡、Android/iOS 真机与听测仍单独保留。

## 3. 一局的房间与导航

一局从还愿庭进入三层主路。每层由清房、供物、借愿、精英、灯摊、可选支路和 Boss 组成，房间图由固定种子生成；地图只读展示已发现节点，不提供传送。玩家必须在当前房间清空波次后，走到实际的南、北、东或西方向门口并沿门的方向穿过阈值，才会进入下一房。回访旧房从对应反向门出生，房间模板、治疗、掉落和领取状态从 `room_history` 恢复。断绳入口也遵守“靠近、停留显露、朝入口走入”的物理规则。

18 个模板由 `room_geometry.gd` 按 `family + variant` 数据驱动：开放、柱阵、折线、回环、桥和侧门各有三种变体。每个模板共享 18×9、64 单位格和同一碰撞查询，地图美术可以换皮但不能改写门阈值、可行走区域或射线阻挡。

四类特殊支路是实际房间类型：献灯房以心火换遗物或上限，判官房以心火换高阶供物或武器，观音房提供治疗、上限或一枚行愿，破阵房完成三轮连续战斗后开放稀有供物。每类房间每局只确认一项；`special_rooms` 与 `growth_log` 在同一保存事务中提交，回访不会重复扣款或发奖。

## 4. 角色、武器与技能

六名角色共享移动、瞄准、身法和焚债输入，但初始武器、三技能、生命、速度、被动和两条本职路线不同：纸童偏焚债回能，铃师偏连债，灯客偏灼烧，傩面偏护甲与招架，伞灵偏位移与回收，墨吏偏穿透与墨契。角色解锁条件写入局外账本，训练和试演不得改变账号成长。

16 件武器由 `mode` 分派到三条真实攻击路径：弧斩/锥击/蓄力月刃使用近战扇面，照骨线使用受墙体阻挡的射线，其余进入带散布、穿透、爆炸、追踪、折返、弹墙、可控纸蝶或蓄力直线参数的通用弹体路径。武器事件携带 `weapon`、`weapon_mode`、方向和是否重击信息，令角色持械覆层、攻击音效、命中特效和击退强度同步。

18 个技能从统一 `cast_skill` 入口结算：先冻结标记者快照，再按链序计算衰减与路线加成，随后执行即时段、延迟段、重复段、地面区域和资源回收。技能的特殊行为可以复用同一快照，因此存档中途恢复时不会重新寻找目标或重复消费标记。

## 5. 敌群、成长、掉落与组合

敌群表只定义基础敌人的身份、生命、速度、预警与攻击语义；精英房把 `elite_variants` 的生命倍率、预警倍率、伤害加成和自然余烬字段直接传入真实生成与死亡结算。精英保留基础敌人 ID 并附带稳定的 `elite_id`，使受击记录、图鉴、复盘和美术资源都能追溯到实际变体；基础敌人和召唤物也从内容表读取余烬值，不能由渲染层或测试夹具补写固定奖励。

六条路线各有六个三阶行愿节点；54 件遗物按稀有度、楼层、路线和叠加上限进入独立奖励流；九类债约通过明确的收益/惩罚改变房间规则。奖励生成、展示、价格检查、领取、库存替换、成长记录和保存构成一个事务，键为 `run_id/room_id/reward_slot`；库存满时先进入替换确认，不会先扣钱再发现无法容纳。

奖励候选在当前楼层有效池中去重，稀有度无可用项时按规则回退；低血治疗使用逐次增加概率和硬保底；商店购买使用独立随机流，武器试射复制当前构筑到无奖励靶场，返回灯摊后钱包、候选、库存和随机游标必须与进入前一致。每日种子只固定日期、规则版本和初始池，不写入局外解锁或路线历史。

组合图鉴中的 24 套联动各由三件真实遗物组成，图鉴只显示拥有进度，不注入隐藏套装奖励。联动效果必须通过主攻、焚债、收灰、身法、招架、清房或偿还钩子产生；任何派生都要标记 `primary`/`secondary`，并受统一预算限制。[组合矩阵](reports/runtime/synergy-matrix-tests.json)逐 ID 触发所有 24 套组合，并另外逐一触发未被组合引用的 `r08`、`r16`、`r24`、`r32`、`r40`、`r48`、`r54` 七个独立钩子。

## 6. 战斗事件顺序

固定 Tick 每帧按以下顺序工作：读取 ActionFrame；更新方向、身法和蓄力；生成主攻；推进敌人、弹体、印区与延迟动作；处理碰撞；记录伤害来源；执行标记/灼烧/债链；结算击退、死亡和掉落；最后发出 HUD、VFX、音频和保存事件。原始伤害只进入一次主结算，次级伤害不能再次启动主触发；敌人死亡先写 `enemy_ledger` 再生成余烬、纸钱和死亡事件。

轻击、重击、焚债和次级伤害有不同的击退距离；普通敌、精英和 Boss 有不同控制衰减。敌弹受墙体、招架、冲刺无敌和护甲规则约束；受击事件保存来源 ID、来源类型、方向、护甲抵消、复活和前后心火，供暂停页本局记录与失败复盘使用。

## 7. UI、输入与反馈

UI 采用 24 单位圆角面板、圆形/胶囊按钮、图标优先信息层级、资源圆体正文和得意黑标题；重复动作文字收进 tooltip 与展开详情，战斗 HUD 只保留心火、香火、方向、武器、技能和门提示。奖励、技能、商店和债约候选支持 PC 数字键 `1/2/3/4` 直选；Tab 打开只读地图，I 打开愿簿，Esc 进入暂停菜单；暂停页的“本局记录”按时间倒序展示初始武器/技能、所有遗物、行愿、债约、武器替换和特殊房交易，并从单局快照恢复。

桌面使用 WASD/方向键移动与瞄准、鼠标或手柄辅助瞄准、左键/扳机攻击、右键/Q 焚债、Space 身法。方向键既能移动也能在无右摇杆时持续瞄准射击。手机采用安全区内双摇杆和大触点，输入适配器只生成同一份 ActionFrame；暂停、横竖屏滞回、辅助瞄准、触觉和减少闪光都在规则层处理。

## 8. 美术与声音锁定

美术统一为纸偶、墨线、朱砂火、铜器和玉灰的平面材质：角色轮廓必须能在小尺寸下区分，房间地面与墙体保持高对比门口，敌方预警使用玉青/朱红，玩家反馈使用暖金/杏橙。角色、手持器具、门、特殊房道具、敌群和 VFX 的尺寸、锚点、透明边及四向朝向以[视觉一致性约定](17-visual-contract.md)和[素材生产规范](11-asset-production.md)为准；后续生成素材必须沿用已批准的 Sub2 参考图，不得把新画风混入运行包。

声音由 29 个音效族各 3 个确定性变体组成，覆盖射击、近战、射线、蓄力、可控弹、轻/重/暴击/护甲/链式命中、普通/重/债约受击、技能、身法、拾取、警告、契约和结算；v3 合成器为攻击、命中与受击加入瞬态、次低频、材质噪声和延迟尾响。新连债会按实际链接数请求短暂张力抬升，二连以上增加低音量铜铃回响，爆发事件保留独立尾音。九套地图主题使用底层、节奏、张力、应答和低音量房间空气纹理的 32 小节分层；战斗、Boss 阶段、暂停和后台只改变分层增益，不改变模拟随机流。来源、许可和滤波处理见[音频来源审计](reports/runtime/audio-source-research.json)与[音频设计验证](reports/runtime/audio-design-verification.json)。

## 9. 存档、跨端与维护门槛

存档 schema 2 同时保存账号与当前局 journal，使用双代副本、SHA-256、IEEE754 浮点编码、旧 schema 迁移、导入预览、失败回滚和中途暂停恢复。任何新增字段都要补迁移默认值、版本验证、旧文件保留和往返测试。Windows、Android 和 iOS 共享 `game/` 内容树；桌面可执行文件、Android APK 和 iOS 共享源码的哈希分别绑定交付清单，不能用静态包一致性代替真机运行。

新增系统的最小交付顺序是：先在 JSON 增加稳定 ID 和规则；再接入 World 的单一结算钩子；补图标、动作、音效和 UI 表现；增加固定 Tick 与存档夹具；运行[方向 01 系统审计](reports/runtime/direction1-system-audit.md)、设计校验、原生 GUI、Android 静态包和跨端一致性；若 `game/` 有变化，重新构建 Windows/Android 并重生成 iOS 交接包。任何自动通过都不能抹掉真人平衡、移动设备、Mac/Xcode 和人耳听测的待验收状态。
